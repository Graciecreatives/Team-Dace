# Supabase authentication and OpenRouter setup

FarmBuddy now includes the official `@supabase/supabase-js` SDK for email/password authentication. Application data still uses the private PostgreSQL snapshot adapter, while photos use private Storage. These are three separate Supabase integrations. OpenRouter remains the server-side gateway for FarmBuddyAI text responses and supported photo requests. YarnGPT is optional for spoken replies.

## 1. Fill your private environment

Use `.env.example` as a reference and copy the relevant settings into your private `.env`. Do not overwrite an existing `.env` or paste keys into chat. No real keys are supplied or generated by this implementation.

| Variable | What to put here | Needed for |
| --- | --- | --- |
| `APP_URL` | Your site origin, e.g. `http://localhost:3000` locally or your HTTPS domain in production | Confirmation email redirect |
| `FARMBUDDY_AUTH` | `supabase` | Supabase email/password auth |
| `SUPABASE_URL` | Your project's HTTPS URL from Supabase project settings | Auth and Storage |
| `SUPABASE_PUBLISHABLE_KEY` | Your project's publishable key | End-user Auth SDK |
| `SUPABASE_ANON_KEY` | Legacy anon key alternative. Leave blank if using the publishable key | Legacy key support |
| `FARMBUDDY_DATABASE` | `supabase` | PostgreSQL application data |
| `SUPABASE_DATABASE_URL` | PostgreSQL connection URI from Connect, with URL-encoded password | Private data snapshot |
| `SUPABASE_SERVICE_ROLE_KEY` | Private service-role key, never an anon/publishable key | Backend-only photo Storage |
| `SUPABASE_STORAGE_BUCKET` | `farm-products` | Private product photos |
| `OPENROUTER_API_KEY` | Your OpenRouter inference API key | AI text/photo replies |
| `OPENROUTER_MODEL` | Namespaced model ID, default `openai/gpt-4.1-mini` | AI model selection |
| `YARNGPT_API_KEY` | Optional YarnGPT key | Spoken replies |
| `YARNGPT_VOICE` | Optional exact voice catalogue name, or blank for default | Voice selection |

All credentials are read by server code. The service-role key and PostgreSQL URI must never be included in browser/public configuration. Auth uses the publishable/anon key, not the service-role key. `GET /api/auth/config` reports only auth mode and a configuration boolean, never keys. A configured flag does not prove project networking, SMTP, billing or model access works.

## 2. Configure the Supabase project

1. Enable the Email provider under Authentication. Decide whether email confirmation is required. Keep confirmation enabled for a public production signup flow.
2. In Authentication > URL Configuration, set Site URL to your application origin and add its `/login` URL to allowed redirects. Add exact local and production URLs you actually use. Production must use HTTPS. Do not allow arbitrary wildcard redirect destinations.
3. The default confirmation email flow is supported: confirm the email using the provider's link, then **sign in with your email and password** on FarmBuddy. The app does not create a dashboard session before confirmation. It strips default confirmation URL fragments and does not trust or store tokens from them. OAuth/magic-link sign-in and password-reset flows are not implemented.
4. Configure an appropriate production email delivery/SMTP setup and review Supabase signup/email rate limits in your project. No real signup emails are sent during automated tests.
5. Provision/import the application database using `docs/SUPABASE_DATABASE.md`. Merely filling the database URI does not initialize or migrate data.
6. Provision the private product-photo bucket using `supabase/product-images.sql` and `docs/PRODUCT_PHOTOS.md`.
7. Restart `npm run host` for local previews. In production configure actual server environment secrets and restart/redeploy the Node server. A `.env` file alone is not automatically loaded by the packaged production entrypoint.

## 3. Authentication behavior and safety

- Signup and password sign-in go through Supabase Auth. New cloud-auth users are associated with a FarmBuddy profile by their immutable, provider-verified Supabase user ID.
- Email-confirmation signup responses show a Check your email screen rather than redirecting into a protected dashboard. No signup metadata can grant roles or bypass onboarding.
- Provider access/refresh tokens are held in HttpOnly, SameSite=Lax cookies with Secure enabled in production. They are never returned in API JSON or stored in browser localStorage. Server verification uses Supabase `getUser`, not unverified JWT decoding.
- Refresh and verification are performed before feature data callbacks. Existing farm ownership checks and explicit public data projections remain in force.
- Missing/invalid explicit Supabase configuration or provider outages do not silently fall back to local passwords. Existing local `farmbuddy_session` cookies are not accepted in Supabase mode.
- Logout clears the current browser's auth cookies and requests local-scope Supabase sign-out. Other devices are not globally signed out. Supabase access JWTs may remain valid until their provider expiry even after refresh-session revocation. Do not assume an already-stolen access token is immediately invalidated by logout.
- Password recovery, password resets, account deletion, MFA and social OAuth are not added by this change. Connected workspace teammate permissions are documented in `docs/CONNECTED_MANAGEMENT.md`.

## 4. Existing local accounts are not automatically migrated

**Switching the database and switching authentication are different operations.** Importing the old JSON snapshot preserves app data but does not create Supabase Auth identities or import old scrypt passwords into Supabase.

There is deliberately no email-based automatic linking. If a newly authenticated Supabase identity has the same email as an unlinked legacy local FarmBuddy account, the app refuses with an account-migration message instead of taking over that account or discarding its records. No password is reset, no account is deleted and no existing ownership is transferred automatically. A separately reviewed, explicit identity migration/linking process is required before moving existing users to cloud auth. Use a genuinely new test account to validate your cloud project first.

For intentional development using old local accounts, select `FARMBUDDY_AUTH=local` and `FARMBUDDY_DATABASE=local`. This preserves the old local workflow without pretending it is Supabase authentication. Never use local JSON on ephemeral/multi-instance production hosting.

## 5. OpenRouter text gateway

The assistant calls the fixed server endpoint `https://openrouter.ai/api/v1/chat/completions` using `OPENROUTER_API_KEY`. No direct OpenAI key, Vercel AI Gateway key or browser SDK is needed. Use a provider/model namespaced `OPENROUTER_MODEL`. The default is supported for text and image input, while unverified custom models remain text-only. Selected farm profile/conversation content is shared with OpenRouter and its routed model provider when you press Send. Set your provider spending limits and review its data policies before rollout.

## Validation and rollout

`npm test` explicitly isolates tests from inherited cloud/AI keys and uses synthetic Auth provider responses. `npm run build` and `npm run test:production` cover packaged local regressions. You must still test signup, real email confirmation, login, refresh, onboarding, account isolation, logout, database persistence and photo privacy against your own configured Supabase project. No live cloud project, paid inference or production email delivery is configured automatically. Dependency audit findings from the existing dependency tree remain a separate deployment security review requirement.
